## Change summary

The project is now runnable end to end. Added the configuration loader, video source with honest
timestamps, YOLO detector wrapper with ground-contact extraction, multi-object tracker, run
pipeline, interactive calibration commands, visualisation and plots, the `cardetect` CLI, a
synthetic ground-truth video generator, and the hand-authored rig diagrams for both mountings.

Test count went from 85 to **105, all passing**, including nine new end-to-end tests that drive the
full measurement chain against synthetic footage with known speeds.

Four genuine defects were found and fixed, two of them unreachable by any test that existed before
this change:

* **The tracker mixed two index spaces.** The IoU matcher returns positions within the sorted track
  list; the proximity fallback inserted *track identities*. The two are not interchangeable because
  identities are monotonic and routinely exceed the number of live tracks, so a successful
  association could raise `IndexError`.
* **`load_calibration` never worked.** `build_projector` only recognised a calibration nested under
  a `calibration:` key, whereas a standalone calibration file has its geometry keys at the top
  level. A calibration could be written and read back, and the resulting error blamed missing
  parameters rather than a shape mismatch.
* **A deprecated Ultralytics flag flooded the console.** `half` was renamed to `quantize` and now
  emits a warning on *every* call, which at thirty frames per second measurably slows the pipeline
  and buries real output. Switching to the new parameter made the run roughly five times faster.
* **The synthetic scenario was physically impossible.** It asked a 0.85 m overhead camera to watch
  a car travel 0.83 m when the entire visible depth at that height is 0.67 m, so the vehicle left
  the frame before the measurement window opened.

## Description of the changes

### 1. Timestamps are the quiet foundation, so they are handled first

`source.py` exists mainly to get time right, because every speed divides by it and the obvious
approach is wrong on the target hardware.

`CAP_PROP_FPS` is an *encoding* property. On a video file it is a header field, so
`frame_index / fps` is exact. On a live device it is a request, not a promise: a Raspberry Pi Camera
Module reports 30 while delivering anything between 4 and 30, and carries no hardware timestamp.
Using the nominal figure there produces speeds wrong by an unknown, time-varying factor — the worst
kind of error, because it is invisible. So the module applies two regimes explicitly: files use the
container rate, live sources use a monotonic clock sampled *after* each successful grab.

`burst` mode implements motion-triggered capture for the Pi Zero 2 W, which cannot run a detector
continuously. It watches by downscaling to 160×90 and differencing, then emits a pre-roll plus a
short clip when motion is detected. Nothing is lost: speed is a per-track quantity, so only frames
containing a vehicle carry information, and those are exactly the frames captured.

### 2. Contact-point selection is a first-class configuration option

`detect.py` owns the largest remaining systematic error source. A bounding box's bottom edge is
close to the road contact patch; the box *centre* is not, and projecting it places the vehicle
ahead of itself on the road. That bias is not constant — it scales with distance — so it cannot be
removed by calibrating height or pitch later.

The implemented strategies are `bottom_center` (default), `bottom_third` (compensates a flank view),
and `center`, which exists **solely so the bias can be measured** on a real rig rather than only
asserted in a comment. `bottom_offset_px` moves the reference point toward the true contact patch;
its sign convention is pinned by a test, because inverting it would double the error it corrects.

### 3. Gating happens before association, deliberately

`pipeline.py` projects and gates each detection's contact point, then associates. The ordering is
load-bearing: a ground homography is defined for every pixel, so a point above the horizon maps to a
finite but *negative* road distance — a position behind the camera. Such a value looks harmless
until it is differenced into a speed. Gating after association would let it enter a track history
first.

### 4. Defect: two index spaces in the tracker

The association loop built a sorted list of track identities and then indexed everything by position.
The IoU matcher correctly returns positions. The proximity fallback inserted **identities** into the
same set. Track identities are monotonic and grow without bound as tracks are created and retired, so
once a few tracks had existed, `track_ids[trk_pos]` raised `IndexError` on a perfectly valid match.

The fix makes the index space explicit and single: `matched_tracks` holds positions only, and
identities are resolved at the point of use. The failure only appeared at all because the synthetic
scenario had been retuned to keep a vehicle measurable for longer, which produced enough
track create/retire churn to expose it — a reminder that a scenario which stops exercising a code
path simply stops testing it, silently.

### 5. Defect: `load_calibration` could never have worked

`build_projector` looked only for a nested `calibration:` block. A standalone calibration document
written by `cardetect calibrate` has its `plane` or `extrinsics` keys at the top level, so it was
rejected with a message about missing parameters. Both shapes are now accepted, along with the
intrinsics that live inside a calibration document.

The round-trip is now asserted on **projected positions** rather than on serialised fields, because a
field-level comparison would pass while the geometry silently differed.

### 6. Defect: a deprecated flag cost 5× throughput

Ultralytics renamed `half` to `quantize` and now emits a deprecation warning on every call. At thirty
frames per second across a 56-frame clip that produced roughly fifty warnings and a run time of
8.5 s; switching to the new parameter and passing it only when a non-default precision is wanted
brought the same run to 1.7 s with no console output. The config key follows.

Precision resolution was also made honest: `auto` enables 16-bit only on CUDA. On CPU, half precision
is slower *and* less accurate, so the obvious "lower precision is faster" rule would silently cost
accuracy on the Raspberry Pi and Orange Pi targets.

### 7. Defect: the synthetic scenario was geometrically impossible

The table-top scenario was hardcoded to move a car 0.83 m. At 0.85 m height and a 70° lens the entire
visible depth is 0.67 m, so the car left the frame at row 817 of 720 before the measurement window
opened. This is a real property of an overhead rig worth documenting rather than a test artefact: a
camera close enough to fill the frame with a table-top track sees only a few tens of centimetres of
road.

Scenarios are now derived from the geometry. A `_visible_depth_span` helper computes the visible
depth, and both rigs' scenarios are sized inside it. The roadside scenario was additionally retuned
to stay inside the *measurable* band rather than merely the frame, because a pitched camera
compresses a distant vehicle's box until its bottom edge no longer corresponds to the near side of
the footprint — a genuine limitation, and the reason the production gates exist.

### 8. End-to-end validation with exact ground truth

`make_synthetic_video.py` builds a scene in **metres**, renders it through the camera model, and
records the exact per-frame box and road position of every vehicle. `tests/test_pipeline_synthetic.py`
then injects those recorded boxes in place of the detector and asserts the chain recovers the drawn
speeds and positions.

The detector is stubbed rather than run, and the reason is stated in the test: a YOLO model trained
on real vehicles does not reliably detect flat coloured rectangles, so running it would test the
model rather than this project. Substituting the truth isolates the layers this project is
responsible for — which are exactly the layers that contained sign errors during development.

The tests are also written to fail if the scenario itself degrades. A scenario whose vehicles are
invisible would let every assertion pass vacuously, so vehicle visibility and the presence of two
simultaneous tracks are asserted before any measurement is checked.

One test deliberately *measures* the box-centre bias on real geometry instead of asserting it in a
comment, so the configuration block's justification is falsifiable.

### 9. Calibration as a first-class command

`calibration.py` implements the tape-measure-and-two-marks workflow that was chosen, with the
limitation handled explicitly rather than papered over. A measured distance constrains scale; it does
not determine a 2D ground homography, because height and pitch trade off — a camera twice as high
aimed twice as steeply sees nearly the same image. For the overhead rig this is harmless, since the
map truly is affine. For the roadside rig one of a horizon row, a lens height or a tilt is required,
and the command solicits it while stating why.

Refusing to guess is the point. A wrong height biases every speed by exactly the height ratio, and
the resulting numbers look entirely reasonable. An error at calibration time is far cheaper.

A horizon can be estimated from a clicked road edge, which is validated to be a poor idea for a
vertical feature: a vertical edge carries no horizon information, and a degenerate division would
otherwise feed a meaningless pitch into the calibration. A recovered height outside 0.05–12 m raises
a warning, since that is the signature of a mis-clicked mark.

### 10. Rig diagrams

`docs/rig-diagrams.svg` is hand-authored, drawn to a common physical scale, and labels the quantities
the calibration actually needs. It deliberately reports the *consequences* of each rig rather than
just its shape: the overhead rig's 0.93 mm/pixel is uniform across the frame, the roadside rig's
2.1 mm/pixel at 1 m becomes 24.3 mm/pixel at 6 m, and the growing positional-error bars show why an
error budget exists at all. A closing section names the two measurements that decide accuracy and
the specific way to get each wrong.

## JUSTIFICATION FOR THE CHANGES

* **Timestamps supplied rather than inferred.** On the primary target hardware the nominal frame rate
  is simply false. A wrong divisor produces a proportional speed error that nothing downstream can
  detect, so the only safe design is to measure elapsed time.
* **Burst capture as a first-class mode.** It is not a compromise for a weak device; it is the correct
  strategy. Since speed is per-track, idle frames contain no information, and a Zero 2 W can afford
  to watch cheaply and analyse only events.
* **Contact point as configuration, not a constant.** The bias is large, distance-dependent and
  invisible in the output. Making it explicit, documented and measurable is the only way to keep it
  under control.
* **Gate before associate.** An invalid projection is a finite, plausible-looking number. The only
  reliable place to stop it is before it can reach a history.
* **Stub the detector in the end-to-end tests.** It isolates the code under test and makes the
  tolerances meaningful; a test that fails because a model cannot see a rectangle teaches nothing
  about this project.
* **Assert scenario validity before asserting measurements.** An end-to-end test that passes
  vacuously is worse than no test, because it creates false confidence.
* **Refuse an under-determined roadside calibration.** The alternative is a silently biased constant
  factor in every reported speed.
* **Measure the box-centre bias rather than describe it.** A claim that justifies a configuration
  block should be falsifiable, and on real geometry rather than in prose.
* **Use the non-deprecated precision API.** A per-frame warning is not cosmetic at thirty frames per
  second; it is measurable throughput, and it buries the run's actual output.
* **Draw the rigs to a common scale.** The overhead and roadside rigs differ by a factor of ten in
  standoff distance, and that difference, not the model choice, is what determines achievable
  accuracy. A drawing that showed them at different scales would hide the very thing it should teach.

  only way to demonstrate that the geometry is right without a track on the table.
